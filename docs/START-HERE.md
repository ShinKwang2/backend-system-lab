# 처음 시작하거나 컴퓨터가 바뀌었을 때

오늘의 목표는 장애를 만드는 것이 아니라 **어느 컴퓨터에서 무엇을 실행할지 확인하는 것**이다. 한 번에 아래 명령을 모두 실행시키지 말고, 튜터가 하나씩 설명하고 실제 출력을 함께 읽는다.

## 1. 터미널과 실행 위치

터미널은 명령을 입력하는 창이고, 셸은 그 명령을 해석하는 프로그램이다. 현재 폴더와 현재 접속한 컴퓨터는 별개다. SSH로 VM에 접속했다면 그 뒤 명령은 VM에서 실행된다.

| 명령 | 확인할 것 | 읽는 방법 |
| --- | --- | --- |
| `pwd` | 현재 폴더 | 출력된 경로가 프로젝트인지 확인 |
| `ls` | 현재 폴더의 파일 | `gradlew`, `build.gradle`, `src`가 보이는지 확인 |
| `uname -s` | 운영체제 종류 | Linux인지 Darwin(macOS)인지 구분 |
| `java -version` | 현재 기본 Java | 버전과 배포판 확인; 프로젝트 toolchain과 다를 수 있음 |

이 명령들은 출력 후 종료한다. Java 버전 출력은 오류 출력 스트림에 표시될 수 있으며, 출력이 있다는 것만으로 실패가 아니다. 모르는 단어는 튜터에게 설명받는다.

## 2. 실행 경로 확인

로컬 작업용 컴퓨터와 격리된 Linux 실험 머신을 구분한다. VM이 아직 없다면 현재 자원과 사용 가능한 가상화 환경을 확인한 뒤 구성한다. 접속 주소·사용자명·프로젝트 경로를 추측하지 않는다.

- 로컬: 편집, Git, 필요 시 기본 빌드 확인.
- Linux 실험 머신: Spring Boot 실행과 `ps`, `top`, `free`, `ss` 등의 관찰.
- DB·캐시·브로커·컨테이너: 현재 입문 과정에 일괄 설치하지 않는다.

## 3. 기본 실행 확인

프로젝트 루트에서 `./gradlew --version`으로 Wrapper가 사용하는 Gradle/JVM 정보를 확인한다. 첫 실행은 의존성 다운로드와 쓰기 가능한 Gradle 캐시가 필요할 수 있다. 실패하면 실제 오류를 기록하고 환경 문제부터 해결한다.

기본 앱을 실행할 준비가 됐다면 `./gradlew bootRun`을 사용한다. 이 명령은 빌드 후 앱을 실행하며 터미널을 계속 사용한다. 같은 터미널의 `Ctrl+C`로 중단한다. 시작 로그에서 실제 포트와 시작 성공 여부를 확인한다. 루트 경로 `/`에는 API가 없으므로 해당 경로의 404 응답만으로 기동 실패라고 판단하지 않는다. CPU 실험 API는 별도 `lab` 프로필에서만 등록된다.

`ps`에서 보이는 Gradle 프로세스와 실제 Spring Boot JVM을 구분하는 것은 CPU-01에서 함께 배운다. 아직 임의의 Java PID를 선택하지 않는다.

## 4. 환경 기록과 첫 수업

확인된 내용을 [ENVIRONMENT.md](ENVIRONMENT.md)에 적는다. 실제로 확인하지 않은 칸은 비워두거나 `미확인`으로 둔다. 재현에 필요한 버전·자원은 기록하되 비밀 값은 넣지 않는다.

첫 수업은 [CPU-01](../src/main/java/com/shinkwang/backendsystemlab/cpu/README.md#cpu-01--spring-boot도-프로세스다)이다. 목표는 CPU 장애 분석이 아니라 Spring Boot의 프로세스를 찾아 PID를 읽는 것이다.

종료 전 [PROGRESS.md](PROGRESS.md)의 마지막 확인 내용과 다음 작은 행동을 갱신한다. AI가 문서를 작성한 것과 학습자가 실습한 것은 구분한다.
