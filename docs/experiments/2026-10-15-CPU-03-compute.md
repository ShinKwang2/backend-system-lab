## 1. 목표와 조건

질문: 한 실행 흐름에서 약 3초간 계산하면 Java 프로세스와 Linux 전체의 CPU 사용률, 요청 응답 시간이 어떻게 달라지는가?

- 별도 학습 VM이며 실제 서비스를 운영하지 않는다고 사용자 확인.
- 사용 가능한 처리 장치 수: nproc 4. Java 21.0.12.1, Gradle 9.7.1, top(procps-ng) 4.0.4.
- 코드: [CpuLabController.java](../../src/main/java/com/shinkwang/backendsystemlab/cpu/CpuLabController.java). 로컬 코드 커밋 fe35463 확인. Linux 실험 시 실제 커밋 해시 출력은 미제공.
- lab 프로필 전용 GET /lab/cpu. nanoTime 차이를 검사하는 순차 산술 루프를 약 3초로 고정.
- 단일 JVM에서 AtomicBoolean으로 동시 계산 1개 제한. 추가 진입은 429, finally에서 진입 상태 복원.
- top 관측 기준: Irix On(CPU 하나분=100%), -d 1로 약 1초 갱신하도록 안내 후 결과를 보고받음.
- 중단: 실행 터미널 Ctrl+C. curl의 취소·timeout만으로 서버 계산이 즉시 중단된다고 가정하지 않음. 루프 자체의 종료 조건을 사용.

## 3. 실험 전 예상과 학습자의 설명

학습자 예상: 요청이 하나이므로 앱 CPU가 약 100%가 될 것 같다.

보완: 이번 코드는 한 실행 흐름이 계산을 순차 반복하므로 CPU 하나분을 예상할 수 있다. 요청 하나가 내부적으로 병렬 작업을 만들 수도 있어 요청 수만으로 CPU 사용 상한을 일반화하지 않는다. 앱 CPU에는 JVM의 다른 활동도 포함되므로 정확히 100.0을 요구하지 않는다.

## 4. 실제 진행 순서와 재현 명령

표의 결과는 실제 제공된 출력·설명이다. 명령 형식은 안내한 값을 함께 남긴 것이며, 별도 보고되지 않은 Git 세부 실행이나 출력은 완료로 만들지 않는다. A와 B는 실행을 유지하고 C에서 요청하는 순서로 진행한다.

### 4-1. Mac 작성·컴파일과 Linux 전달

학습자가 컨트롤러와 계산·진입 제한 코드를 작은 단계로 작성했다. 초기 세미콜론 누락을 수정했고, compareAndSet의 expected/new 값 관계와 원자적 진입 제한을 질문·학습했다.

Mac M:

```bash
./gradlew compileJava
```

실제 제공 출력:

```text
BUILD SUCCESSFUL in 3s
1 actionable task: 1 executed
```

Configuration Cache 권고는 선택적 성능 안내로 읽고 설정을 변경하지 않았다. 컴파일 성공을 테스트·실행 성공으로 확대하지 않았다.

전달 순서: Mac commit/push → Linux pull. 안내한 push와 pull 명령은 다음과 같다.

```bash
# Mac M
git push origin main
```

```bash
# Linux A
cd /home/skl/backend-system-lab
git pull --ff-only origin main
```

사용자가 push·pull 성공을 보고했다. 실제 add/commit 선택 범위와 Linux 해시 출력은 별도로 제공하지 않았다. 기록 정리 시 로컬 Git에 수정 문서와 미추적 실험 기록이 남아 있어 문서 전체가 원격 반영됐다고 확정하지 않는다.

### 4-4. 요청 전 CPU 관찰

Linux B에서 기존 top이 있으면 q로 종료한 뒤:

```bash
top -d 1 -p 52288
```

- -d 1: 약 1초 갱신. -p: 앱의 프로세스 행만 선택.
- Irix On 기준으로 맞추도록 안내했다. Shift+i를 누르면 On/Off가 전환되고 바뀐 상태가 표시됨.
- 실제 보고: 요청 전 앱 CPU는 주로 0.0%, 가끔 0.6%. 각 갱신의 원본 화면·시각은 미제공.
- 상단 %Cpu(s)는 앱 한 개가 아니라 Linux 전체 상태다.

### 4-5. 계산 요청 하나와 회복

Linux A·B는 유지하고 C에서 한 번 실행:

```bash
curl -i --max-time 10 http://localhost:8080/lab/cpu
```

실제 보고: 계산 중 앱 CPU가 약 100으로 올라갔다가 다시 낮아짐. 회복 후 정확한 숫자는 미제공.

실제 응답에서 발췌:

```text
HTTP/1.1 200
Content-Type: text/plain;charset=UTF-8
Date: Thu, 15 Oct 2026 23:16:15 GMT

254259729904475773
```

본문은 산술 루프의 최종 long 값을 문자열로 바꾼 것이다. CPU 사용률·경과 시간이 아니다. result는 1 → 38 → 1185 → 36742처럼 변하며, long 범위를 넘으면 값이 순환하고 음수도 가능하다. 반복 횟수를 고정하지 않아 호출마다 결과가 달라질 수 있다.

### 4-6. 겹치는 요청의 거절

첫 계산이 진행 중일 때 별도 요청 터미널에서 같은 curl을 실행하도록 검증했다. 사용자가 다른 터미널에서 시도했다며 다음 실제 응답을 제공했다.

```text
HTTP/1.1 429
Content-Type: application/json
Date: Thu, 15 Oct 2026 23:18:38 GMT

{"timestamp":"2026-10-15T23:18:38.354Z","status":429,"error":"Too Many Requests","path":"/lab/cpu"}
```

같은 터미널에서도 겹쳐 보낼 수 있음을 다음 명령으로 안내했다. 두 줄을 연속 실행하며 &는 셸이 첫 curl 종료를 기다리지 않고 다음 명령을 받게 한다.

```bash
curl -i --max-time 10 http://localhost:8080/lab/cpu &
curl -i --max-time 10 http://localhost:8080/lab/cpu
```

사용자는 잘 해봤다고 보고했다. 이 두 요청의 개별 응답 전체·정확한 겹침 시각은 미제공이다. 출력이 같은 터미널에 섞일 수 있다. 기존 429 응답을 새 요청의 결과로 다시 만들지 않는다.

### 4-7. 요청 경과 시간과 서버 전체 CPU

계산 요청이 끝난 뒤 Linux C에서 요청 하나를 전경 실행:

```bash
curl --max-time 10 -w '\nHTTP %{http_code}, total %{time_total}s\n' http://localhost:8080/lab/cpu
```

- -w: 전송 후 지정한 정보 출력.
- %{http_code}: HTTP 상태 코드. %{time_total}: 클라이언트 전체 전송 경과 시간.
- \n: 출력 줄바꿈. --max-time 10: 클라이언트의 요청 시간 상한이며 서버 계산 설정 3초와 구분.
- Linux B에서는 같은 top의 서버 전체 us·sy·id를 관찰.

사용자 제공 출력:

```text
-7848091344360240255
HTTP 200, total 3.002366s
```

함께 보고한 서버 전체 값: 계산 중 us 약 25%, id 약 75%. sy의 구체적 값은 미제공이다. 이 값들을 반드시 같은 갱신 순간에 찍힌 원본 한 줄이라고 확대하지 않는다.

앞서 time_total을 요청했을 때 -w 없는 429 출력이 다시 제공돼, 그때는 경과 시간을 미확인으로 유지했다. 위의 HTTP 200·3.002366s 출력이 제공된 후에 실제 측정값으로 기록했다. 429 거절 시간과 계산 성공 시간을 혼동하지 않는다.

## 5. 결과 해석과 학습자의 설명

- 앱 CPU 약 100%와 서버 전체 us 약 25%는 CPU 4개 중 한 개분을 주로 사용한 흐름과 맞는다. 특정 코어에 고정됐다고 측정한 것은 아니다.
- 학습자는 Java/JVM의 사용자 모드 계산으로 us가 올라가고 id가 내려갔으며 파일시스템 같은 커널 작업이면 sy가 오를 수 있다고 설명했다.
- 보완: JVM도 시스템 호출로 커널 코드를 실행할 때 sy를 사용할 수 있다. 이번에 sy가 전혀 없었다고 확정하지 않는다. 장치 응답 대기 시간과 커널이 CPU를 쓰는 시간은 구분한다.
- 단일 순차 계산 흐름이라는 근거로 실험 전 약 100% 예상을 뒷받침했다. 모든 단일 요청이 CPU 하나만 쓴다는 법칙은 아니다.
- HTTP 200·약 3.002초 응답은 약 3초 루프 설정과 일치한다. 이 경과 시간은 CPU 실행 시간 자체가 아니며 내부 구간별 시간은 분해 측정하지 않았다.
- 정상 → 계산 → 회복을 관찰했고, 추가 진입 거절 429도 확인했다. CPU 전체를 고갈시킨 실험으로 서술하지 않는다.
