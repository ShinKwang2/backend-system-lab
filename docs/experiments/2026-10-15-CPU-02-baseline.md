# CPU-02 — 정상 상태 CPU 읽기

상태: 완료 · 관찰일: 2026-10-15(KST) · 환경: E01

## 목표와 관찰 조건

정상 앱의 CPU 표시를 읽고 프로세스와 서버 전체의 범위·분모·갱신 구간을 구분한다. CPU-01에서 재실행한 앱 PID 47487을 사용했다. 장애 부하는 주입하지 않았다.

- Linux A: 앱 실행 유지.
- Linux B: top 관찰. 프로젝트 밖에서도 실행 가능.
- Linux C: 같은 VM에서 HTTP 요청.
- 과거 PID 47487은 이번 기록의 값이다. 재현 시 실제 앱 PID로 바꾼다.

## 실제 진행 순서

| 순서 | 위치 | 명령·조작 | 목적·확인 결과 |
| --- | --- | --- | --- |
| 1 | B | `top -p 47487` | 앱 행 PID·%CPU·COMMAND 확인. 0.0, 잠깐 0.3 |
| 2 | B | `q`, 이어서 `nproc` | 사용 가능한 처리 장치 수 4 |
| 3 | B | `top -p 47487` | 프로세스와 전체 CPU 표시 기준 학습 |
| 4 | B의 top | `Shift+i` 1회 | 전환 후 Irix mode Off 확인 |
| 5 | 같은 화면 | `Shift+i` 1회 더 | 전환 후 Irix mode On 확인 |
| 6 | C | `curl -i --max-time 5 http://localhost:8080/actuator/health` | HTTP 200·UP. 요청 전후 앱 CPU 잠깐 4.3 |
| 7 | B의 top | 상단 `%Cpu(s)` 읽기 | us 0.3, sy 0.1, id 99.5 등 실제 한 줄 확보 |
| 8 | B의 top | 소문자 `h` | procps-ng 4.0.4, Delay 3.0 secs 확인 |

도움 화면은 Esc로 관찰 화면에 돌아가고, top은 q로 종료한다. 이 키 사용법을 안내했으나 마지막 top 종료 여부는 별도 보고받지 않았다.

## 명령과 출력 읽는 법

- `top -p <APP_PID>`: 아래 프로세스 목록을 해당 PID로 제한한다. 상단 CPU 요약은 Linux 전체다.
- `nproc`: 현재 명령이 사용 가능한 CPU 처리 장치 수. 물리 칩 수나 VM 설정 전체를 확인하는 명령은 아니다.
- `Shift+i`: Irix 표시 모드 전환. 메시지는 바뀐 후의 상태다.
- Irix On: CPU 하나분을 100%로 표시. Off: CPU 수로 나눠 전체 용량 기준으로 표시.
- `curl -i`: 응답 헤더 포함. `--max-time 5`: 클라이언트 요청 전체 대기 상한 5초.
- 상단 `us`: 사용자 공간 CPU 시간, `sy`: 커널 CPU 시간, `id`: 유휴 시간. 전체 CPU를 기준으로 집계.
- `h` 도움 화면의 Delay: 갱신 간격. 앱 실행 주기가 아니라 관측 화면 갱신 설정이다.

## 실제 출력과 관찰

| 구간 | 앱 CPU 표시 | 제한 사항 |
| --- | --- | --- |
| 첫 요청 없는 관찰 | 0.0, 잠깐 0.3 | 이 세션의 Irix 모드는 직접 확인 전 |
| Irix On 확인 후 가벼운 요청 | 잠깐 4.3 | 작업 하나의 CPU 비용이나 순간 최대값으로 단정하지 않음 |

HTTP 응답:

```text
HTTP/1.1 200
Content-Type: application/vnd.spring-boot.actuator.v3+json
Transfer-Encoding: chunked
Date: Thu, 15 Oct 2026 04:04:31 GMT

{"groups":["liveness","readiness"],"status":"UP"}
```

서버 전체 CPU:

```text
%Cpu(s):  0.3 us,  0.1 sy,  0.0 ni, 99.5 id,  0.1 wa,  0.0 hi,  0.0 si,  0.1 st
```

도움 화면:

```text
Help for Interactive Commands - procps-ng 4.0.4
Window 1:Def: Cumulative mode Off.  System: Delay 3.0 secs; Secure mode Off.
```

## 해석과 학습 내용

- 표시 0.0은 작은 사용량과 표시 정밀도 때문에 나올 수 있다. 앱 종료나 앞으로도 사용량이 0이라는 뜻이 아니다. 잠깐 0.3이 나온 원인을 특정 JVM 작업으로 확정하지 않았다.
- CPU 하나 기준 프로세스 100%는 4개 전체 용량 기준으로는 약 25%에 해당한다. 이 단계에서는 표시 기준 설명용 예시였고, 실제 높은 계산 부하는 CPU-03에서 관찰했다.
- '위 표의 방식'이라는 설명이 모호하다는 학습자의 지적에 따라 분모를 명시했다. 학습자는 다른 부하가 없을 때 나머지 CPU 용량에 여유가 있음을 설명했다.
- top -p로 앱만 목록에 보여도 상단 요약은 전체라는 학습자의 확인 질문을 다뤘다.
- 일반적인 연속 갱신은 이전 갱신부터 이번 갱신까지의 구간을 읽는다. 약 3초 갱신이면 0~3초, 3~6초 같은 연속 구간이며 1초마다 최근 3초를 겹쳐 읽는 방식과 구분했다. 실제 경과 시간을 사용한다.
- Irix On에서 정확히 3초 구간의 4.3%라면 약 0.129초의 CPU 시간이라는 계산 예시를 설명했다. 이를 실측된 단일 요청 CPU 비용으로 기록하지 않았다.
- health UP은 해당 health 요청의 결과다. 개별 probe나 모든 기능의 정상을 검증했다고 확대하지 않는다.

## 완료 범위와 한계

CPU 표시 읽기·범위·분모·간격을 배우고 실제 값과 HTTP 응답을 기록했다. 앞선 별도 세션의 모드 미확인 값은 엄밀한 동일 조건 벤치마크와 구분한다. 장기 정상 범위, 특정 스레드·메서드의 CPU 원인, 실제 단일 요청 CPU 비용은 미확인이다.
