# SCHEDULER-03 — Load와 CPU 정상 상태 관찰

상태: 진행 중

## 1. 질문과 실험 조건

- 날짜 / 환경 ID: 2026-11-20 / E01 학습용 Linux VM
- 오늘 알아볼 질문: CPU 사용률이 낮을 때 load average가 높다면 어떤 작업 대기가 가능하며 무엇을 더 관찰할까?
- 앱·도구·DB 등 실제 버전: Linux VM. vmstat와 ps 실행을 확인했으며 상세 버전은 미확인.
- vCPU / 메모리 / JVM 옵션 / GC / 스레드 설정: 기존 환경 기록 기준 nproc 4. 이번 출력과 동시에 다시 확인하지 않음.
- 이번에 바꿀 조건 하나: 정상 상태에서 도구별 관측을 추가.
- 실험 프로필 / 자원 상한 / 중단 조건 / 정리 방법: 부하 주입 없음. 각 명령은 정해진 출력 후 종료.

## 2. 필요한 개념과 도구

- `r`: 실행 중이거나 CPU 실행 차례를 기다리는 작업 수.
- `b`: 끊기 어려운 대기 상태의 작업 수.
- `wa`: CPU가 I/O 완료를 기다리며 유휴였던 시간 비율.
- `vmstat -w 1 5`: Linux 관찰 터미널에서 실행. wide 형식으로 1초 간격 보고서 5개 출력 후 종료.
- `ps -eo state,pid,comm | head -n 15`: 상태·PID·명령 이름을 골라 처음 15줄을 확인. 표본에 D가 없어도 순간적인 D 상태가 전혀 없었다고 증명하지 않음.
- `uptime`: 실행 시각·가동 시간·사용자 수·1/5/15분 load average 출력 후 종료. load average는 작업 수의 평균이며 백분율이 아님.

## 3. 예상

- 학습자는 CPU가 낮고 load가 높다면 파일 I/O나 네트워크 I/O 대기일 수 있다고 제안했다.
- 일반 소켓 응답 대기는 보통 Linux D 상태로 분류되지 않는다고 안내했다. 디스크·블록 장치 등 커널의 중단하기 어려운 대기는 D 상태로 관찰될 수 있다.

## 4. 실행 순서와 재현 절차

| 순서 | 컴퓨터·터미널 / 작업 폴더 | 정확한 명령 | 목적·볼 항목 | 실제 결과 |
| --- | --- | --- | --- | --- |
| 1 | Linux VM, root@backend-lab, /tmp | `vmstat -w 1 5` | r, b, us, sy, id, wa. 1초 간격 5개 보고서 | 사용자 제공 출력 확인 |
| 2 | Linux VM, root@backend-lab, /tmp | `ps -eo state,pid,comm | head -n 15` | state, PID, 명령 이름. 처음 15줄 | 사용자 제공 출력 확인, 표시된 상태는 S/I이며 D 없음 |
| 3 | Linux VM, root@backend-lab, /tmp | `uptime` | load average 1/5/15분 | 사용자 제공 출력 확인 |

## 5. 정상 상태 관찰

`vmstat -w 1 5`의 첫 행은 부팅 이후 평균을 포함할 수 있다. 이후 네 구간은 r=0,0,0,1, b=0, us=1,0,0,0%, sy=0,1,0,1%, id=99%로 제공됐다. 모든 행에서 wa=0%였다.

ps 출력에 보인 PID 1~17은 S 또는 I 상태였다. 그 표본에는 D 상태가 없었다.

`uptime` 출력은 `06:06:19 up 23:24, 3 users, load average: 0.06, 0.10, 0.09`였다. 이는 1/5/15분 평균이며 기록된 기존 nproc 4와 비교해 낮은 값이다.

## 6. 관찰 사실과 가설

- 관찰 사실: 짧은 기준 관찰에서 b와 wa가 0이고 id가 99%였으며, ps 표본에 D 상태가 없었다. uptime의 세 load average도 0.06~0.10이었다.
- 해석: 해당 관찰 시점에는 높은 load나 뚜렷한 I/O 대기 징후가 보이지 않았다.
- 가설: 만약 CPU 사용률은 낮고 load가 높다면, 실행 대기 작업 또는 D 상태의 중단하기 어려운 작업이 원인 후보일 수 있다.
- 미확인: 실제 높은 load 상황, D 상태의 원인 및 특정 디스크·네트워크 작업과의 인과 관계.

## 7. 다음 행동

load average와 r/b의 관계를 학습하고, 낮은 CPU와 높은 load가 함께 나타나는 실제 출력이 있을 때 추가 지표를 골라 확인한다. 이번 관찰만으로 장애를 만들거나 원인을 확정하지 않는다.
