# Concurrency / 락과 데이터 정합성

여러 실행 흐름의 간섭을 재현하고 정확성·성능·다중 인스턴스 관점으로 해결을 비교한다.

전체 위치와 순서: [CURRICULUM.md](../../../../../../../docs/CURRICULUM.md) · [현재 진도](../../../../../../../docs/PROGRESS.md)

## 시작 조건

CONCURRENCY-01~02는 Thread 심화 후 H03. 03~05는 트랜잭션·MVCC·Pool 후 H07.

## 첫 설명

각 작업이 혼자 실행될 때 맞는 코드도 여러 작업이 같은 값을 함께 읽고 바꾸면 틀릴 수 있다. 먼저 어떤 결과를 반드시 지켜야 하는지 정하고 그 보장을 실험한다.

## 도구를 처음 사용할 때

아래 표는 명령어 사전이다. 첫 수업에서는 필요한 명령 하나와 출력 항목 2~3개만 소개한다. `<PID>`, `<PORT>`, `<PATH>`, `<실험경로>`는 실제 값으로 바꾸는 자리 표시자이며 그대로 실행하지 않는다. 아직 없는 API나 설정은 해당 단계에서 함께 만든다.

| 명령·도구 | 목적과 입력 | 처음 읽을 항목·종료 |
| --- | --- | --- |
| 스레드 덤프 | monitor 진입 대기와 소유 관계를 읽는다. | BLOCKED·잠금 식별자·보유/대기 스레드. 반복 덤프로 확인. |
| 동시 요청 도구 | 작은 고정 동시성부터 시작해 요청 수·시간 상한을 정한다. | 성공·실패·처리량·응답 시간과 실제 최종 데이터. 도구 이름·버전은 도입 시 기록. |
| DB 쿼리·잠금 조회 | 발급·재고 데이터의 불변 조건과 잠금 관계를 확인한다. | 요청 성공 수와 저장 데이터 수를 별도로 비교. |

## 세부 커리큘럼

### CONCURRENCY-01 — 락 경쟁

- 배울 것: critical section, synchronized monitor, 상호 배제와 직렬화를 배운다.
- 안내 실습: 짧은 임계 구역을 둔 제한된 요청에서 정상과 경쟁을 비교한다. CPU·지연·BLOCKED와 소유자를 관찰한다.
- 예상·가설 질문: CPU가 낮아도 처리량이 낮을 수 있을까? 락 범위를 줄이면 무엇이 달라질까?
- 완료 기준: 대기 스레드와 락 보유 코드를 연결하고 범위 변경 후 같은 조건으로 비교한다.

### CONCURRENCY-02 — 서로 기다리는 Deadlock

- 배울 것: 순환 대기와 lock ordering을 배운다. CAS와 원자성은 후속 비교 개념으로 분리한다.
- 안내 실습: 별도 JVM에서 두 락의 역순 획득을 통제해 재현하고 덤프를 읽는다. 별도 프로세스 종료를 복구 방법으로 준비한다.
- 예상·가설 질문: 스레드 두 개가 멈추면 서버 전체가 항상 멈출까?
- 완료 기준: 잠금 관계의 순환을 설명하고 획득 순서 통일 후 재검증한다.

### CONCURRENCY-03 — 쿠폰 100개와 불변 조건

- 배울 것: race condition, 읽기-검사-쓰기, atomicity와 lost update를 배운다.
- 안내 실습: 발급 수가 재고를 넘지 않아야 한다는 조건을 먼저 정한다. 한 인스턴스에서 제어된 동시 실행으로 경쟁을 재현한다.
- 예상·가설 질문: 요청 응답 성공 수와 실제 발급 데이터 수가 같을까? 재현이 안 되면 코드가 안전한 걸까?
- 완료 기준: 재현 조건과 실제 데이터로 위반을 설명한다. 초과 발급 숫자를 미리 정답으로 정하지 않는다.

### CONCURRENCY-04 — 해결책의 보장 비교

- 배울 것: JVM synchronized, DB pessimistic/optimistic lock, atomic UPDATE와 재시도를 배운다.
- 안내 실습: 한 방법씩 구현하고 동일 부하에서 정확성·실패·지연·처리량을 비교한다. optimistic lock은 충돌 처리도 관찰한다.
- 예상·가설 질문: 정확성은 같아도 처리량과 실패 방식은 어떻게 다를까?
- 완료 기준: 조건·보장·비용·오류 처리의 비교표를 남긴다.

### CONCURRENCY-05 — 인스턴스가 두 개라면

- 배울 것: 프로세스 경계와 공유 저장소의 조정 범위를 배운다.
- 안내 실습: 같은 DB를 사용하는 두 앱으로 반복한다. 필요할 때 Redis 분산 락의 만료·소유권·실패를 선택 심화로 추가한다.
- 예상·가설 질문: synchronized의 보호 범위는 어디까지일까? 락이 만료된 뒤 오래된 작업이 쓰면 어떻게 될까?
- 완료 기준: 다중 인스턴스의 정확성을 검증하고 분산 락을 만능 해결책으로 취급하지 않는다.

## 해석할 때 지킬 경계

deadlock은 영향을 받은 작업부터 관찰한다. 항상 서버 전체가 중단된다고 서술하지 않는다. 정합성 확인을 성능 측정보다 먼저 하고, 재현 실패를 안전성 증명으로 취급하지 않는다.

## 수업과 기록

각 단계에서 기초 설명 → 정상 관찰 → 예상 → 조건 하나 변경 → 실제 관찰 → 가설과 검증 → 정리 순서로 진행한다. 도구 입문은 장애 주입이나 해결이 없어도 된다. 첫 실험은 안내형, 반복 실험은 힌트형, 마지막 적용은 독립형으로 도움을 줄인다.

실제 출력과 자기 설명은 [실험 기록 양식](../../../../../../../docs/EXPERIMENT-TEMPLATE.md)으로 남긴다. 현재 이 문서는 계획이며 어떤 단계도 완료로 표시하지 않는다. 다음 단계는 고정된 날짜가 아니라 실제 관찰과 이해를 확인한 뒤 선택한다.
