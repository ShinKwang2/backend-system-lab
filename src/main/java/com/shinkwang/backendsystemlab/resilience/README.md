# Resilience / Retry와 장애 격리

의존성 실패가 요청 수와 대기를 증폭시키는 과정을 보고 복구 정책을 비교한다.

전체 위치와 순서: [CURRICULUM.md](../../../../../../../docs/CURRICULUM.md) · [현재 진도](../../../../../../../docs/PROGRESS.md)

## 시작 조건

외부 API 지연·timeout, Pool, 멱등성. 처음에는 A·B 두 앱만 사용한다.

## 첫 설명

실패한 작업을 다시 시도하면 일시적인 문제를 넘길 수 있지만, 실패 중인 서버에 더 많은 작업을 보내기도 한다. 복구는 성공 가능성과 추가 부하를 함께 고려해야 한다.

아래 표는 명령어 사전이다. 첫 수업에서는 필요한 명령 하나와 출력 항목 2~3개만 소개한다. `<PID>`, `<PORT>`, `<PATH>`, `<실험경로>`는 실제 값으로 바꾸는 자리 표시자이며 그대로 실행하지 않는다. 아직 없는 API나 설정은 해당 단계에서 함께 만든다.

## 세부 커리큘럼

### RESILIENCE-01 — 재시도가 부하를 늘릴 때

- 배울 것: retry 횟수와 attempt 횟수, 전체 시간 예산, 재시도 가능한 실패를 배운다.
- 안내 실습: 제한된 요청에서 재시도 없음과 고정 재시도를 비교한다. 최대 시도·총 시간·취소를 먼저 정한다.
- 예상·가설 질문: 원 요청 10개에서 실제 호출은 몇 번이 됐나? 여러 계층의 retry가 겹치면 어떨까?
- 완료 기준: 실제 호출 수와 누적 지연을 기록하고 업무의 멱등성 필요를 설명한다.

### RESILIENCE-02 — Backoff와 Jitter

- 배울 것: 간격 증가·분산, deadline과 회복 부하를 배운다.
- 안내 실습: 같은 실패·회복 타임라인에서 고정 간격과 backoff+jitter를 비교한다.
- 예상·가설 질문: 회복 시점에 요청이 동시에 몰리는 현상은 어떻게 볼까?
- 완료 기준: 시간대별 시도 수와 성공·지연을 비교하고 모든 실패에 retry를 적용하지 않는다.

### RESILIENCE-03 — Circuit Breaker와 Bulkhead

- 배울 것: 실패 시 빠른 거절, 회복 탐색, 동시 작업 격리를 배운다.
- 안내 실습: 필요성이 확인된 뒤 라이브러리를 정하고 상태 전이·동시성 상한을 작은 실험으로 검증한다.
- 예상·가설 질문: 차단으로 보호받는 자원은 무엇이고 사용자는 어떤 응답을 받나?
- 완료 기준: 고장 중 다른 요청의 영향과 회복 후 결과를 비교하고 timeout·retry·격리 역할을 구분한다.

## 해석할 때 지킬 경계

retry 정책은 오류 종류·멱등성·시간 예산을 기준으로 정한다. circuit breaker나 bulkhead는 발생한 장애 원인을 제거하는 기능과 구분하며 거절·대기·회복 동작까지 검증한다.

## 수업과 기록

각 단계에서 기초 설명 → 정상 관찰 → 예상 → 조건 하나 변경 → 실제 관찰 → 가설과 검증 → 정리 순서로 진행한다. 도구 입문은 장애 주입이나 해결이 없어도 된다. 첫 실험은 안내형, 반복 실험은 힌트형, 마지막 적용은 독립형으로 도움을 줄인다.
