# Network / TCP와 외부 API

HTTP 요청의 지연을 JVM 스레드와 Linux 소켓 상태에 연결한다.

전체 위치와 순서: [CURRICULUM.md](../../../../../../../docs/CURRICULUM.md) · [현재 진도](../../../../../../../docs/PROGRESS.md)

## 시작 조건

기초 5개 주제. NETWORK-01~02는 F06, NETWORK-03~05는 H04에서 진행한다.

## 첫 설명

IP는 통신할 주소를, 포트는 그 컴퓨터 안의 통신 창구를 구분한다. 소켓은 프로그램이 통신하는 끝점이다. HTTP 요청은 그 아래의 TCP 연결을 통해 전달될 수 있다.

## 도구를 처음 사용할 때

아래 표는 명령어 사전이다. 첫 수업에서는 필요한 명령 하나와 출력 항목 2~3개만 소개한다. `<PID>`, `<PORT>`, `<PATH>`, `<실험경로>`는 실제 값으로 바꾸는 자리 표시자이며 그대로 실행하지 않는다. 아직 없는 API나 설정은 해당 단계에서 함께 만든다.

| 명령·도구 | 목적과 입력 | 처음 읽을 항목·종료 |
| --- | --- | --- |
| `curl -v --max-time 5 http://localhost:<PORT>/<PATH>` | 실제 앱 포트와 준비한 경로로 HTTP 요청을 보낸다. `-v`는 통신 정보, `--max-time 5`는 이 클라이언트 요청의 전체 시간 상한(초)이다. | 접속 대상·상태 코드·실패 단계. 요청 종료 또는 Ctrl+C. 앱 서버의 timeout 설정과 구분한다. |
| `ss -ltn` | Linux TCP의 수신 대기 소켓을 숫자 주소로 본다. `-l`은 listen, `-t`는 TCP, `-n`은 숫자 표시다. | LISTEN·Local Address:Port. 출력 후 종료. |
| `ss -tan` | Linux TCP 소켓의 여러 상태를 숫자 주소로 본다. `-a`는 모든 상태다. | State·Local/Peer Address:Port. 출력 후 종료. 어떤 머신에서 수집했는지 기록. |
| `jcmd <PID> Thread.print` | 느린 요청 구간의 Java 호출 스택을 읽는다. | 스레드 이름·상태·네트워크 라이브러리 스택. 출력 후 종료; 상태만으로 대기를 판정하지 않는다. |

## 세부 커리큘럼

### NETWORK-01 — 요청을 받는 포트

- 배울 것: 클라이언트·서버, IP·포트, HTTP 상태와 TCP 연결의 차이를 배운다.
- 안내 실습: 앱의 실제 포트를 확인하고 `ss -ltn`과 curl을 연결한다. 먼저 간단한 응답 경로가 필요하면 함께 만든다.
- 예상·가설 질문: HTTP 404와 TCP 접속 실패는 같은 문제일까?
- 완료 기준: 실제 수신 포트와 요청 결과, 명령을 실행한 머신을 설명한다.

### NETWORK-02 — 연결된 두 끝점

- 배울 것: LISTEN·ESTABLISHED, 로컬/원격 주소, TCP 연결의 기초를 배운다.
- 안내 실습: 별도 포트의 Spring A·B가 필요해지는 이유를 설명한 뒤 구성한다. 짧은 요청과 제한된 지연 요청에서 `ss`를 비교한다.
- 예상·가설 질문: HTTP 요청 하나와 TCP 연결 하나가 항상 일대일일까?
- 완료 기준: 두 앱의 주소·포트와 관측 소켓을 연결하고 짧은 연결을 놓칠 수 있음을 설명한다.

### NETWORK-03 — 외부 API가 느려질 때

- 배울 것: blocking I/O, 요청 스레드 점유, 동시성·처리량을 배운다.
- 안내 실습: B에 제한된 지연을 넣고 A에서 호출한다. curl 전체 시간 상한은 주입 지연보다 길게 조정하고 요청 동시성을 작은 값부터 늘린다. 지연·CPU·덤프·소켓을 같은 구간에 관찰한다.
- 예상·가설 질문: CPU가 낮아도 요청이 밀릴 수 있을까? 스레드 상태만으로 외부 API 대기를 알 수 있을까?
- 완료 기준: Application 지연 ↔ JVM 스택 ↔ Linux 연결의 근거를 묶어 설명한다.

### NETWORK-04 — 어느 단계에서 Timeout인가

- 배울 것: 연결 수립, 응답 읽기, 풀 획득, 요청 전체 제한의 차이를 실제 HTTP 클라이언트 기준으로 배운다.
- 안내 실습: 사용할 클라이언트와 버전을 먼저 정하고 공식 문서에서 설정 의미를 확인한다. 느린 응답과 연결 수립 지연을 격리된 환경에서 따로 재현한다.
- 예상·가설 질문: connection refused가 connect timeout과 같을까? 읽기 timeout이 요청 전체 제한일까?
- 완료 기준: 설정 이름·대상 단계·예외·실제 경과 시간을 대응시킨다. 즉시 거절을 timeout 재현으로 기록하지 않는다.

### NETWORK-05 — 연결 종료 상태

- 배울 것: TCP 종료 흐름, TIME_WAIT·CLOSE_WAIT와 연결 재사용을 배운다.
- 안내 실습: 연결 재사용 유무와 정상/비정상 자원 해제를 비교하며 양쪽 소켓을 시간에 따라 본다. 자원 수와 실험 시간을 제한한다.
- 예상·가설 질문: TIME_WAIT가 보이면 항상 장애일까? CLOSE_WAIT가 오래 누적되면 무엇을 더 볼까?
- 완료 기준: 관측한 종료 상태와 앱의 자원 해제 경로를 연결하고 미확인 원인은 남겨둔다.

## 해석할 때 지킬 경계

ESTABLISHED는 연결 상태이며 응답이 빠르거나 업무가 정상이라는 증거는 아니다. 외부 API socket 대기가 항상 Java WAITING으로 보이는 것도 아니다. timeout 용어와 구현은 클라이언트마다 다르므로 라이브러리를 정한 뒤 문서를 확인한다.

## 수업과 기록

각 단계에서 기초 설명 → 정상 관찰 → 예상 → 조건 하나 변경 → 실제 관찰 → 가설과 검증 → 정리 순서로 진행한다. 도구 입문은 장애 주입이나 해결이 없어도 된다. 첫 실험은 안내형, 반복 실험은 힌트형, 마지막 적용은 독립형으로 도움을 줄인다.

실제 출력과 자기 설명은 [실험 기록 양식](../../../../../../../docs/EXPERIMENT-TEMPLATE.md)으로 남긴다. 현재 이 문서는 계획이며 어떤 단계도 완료로 표시하지 않는다. 다음 단계는 고정된 날짜가 아니라 실제 관찰과 이해를 확인한 뒤 선택한다.
