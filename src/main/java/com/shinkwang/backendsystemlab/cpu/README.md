# CPU / Process

Spring Boot를 Linux 프로세스로 찾고, CPU 사용 변화에서 출발해 계산 중인 Java 코드까지 추적한다.

전체 위치와 순서: [CURRICULUM.md](../../../../../../../docs/CURRICULUM.md) · [현재 진도](../../../../../../../docs/PROGRESS.md)

## 시작 조건

F00 환경 확인. CPU-04는 Thread 입문과 스레드 덤프 읽기를 마친 뒤 진행한다.

## 첫 설명

프로세스는 실행 중인 프로그램이고 PID는 그 프로세스를 구분하는 번호다. 스레드는 프로그램 안에서 실행되는 흐름이며 CPU는 그 작업의 계산을 수행한다. 먼저 앱을 찾는 것부터 시작한다.

## 도구를 처음 사용할 때

아래 표는 명령어 사전이다. 첫 수업에서는 필요한 명령 하나와 출력 항목 2~3개만 소개한다. `<PID>`, `<PORT>`, `<PATH>`, `<실험경로>`는 실제 값으로 바꾸는 자리 표시자이며 그대로 실행하지 않는다. 아직 없는 API나 설정은 해당 단계에서 함께 만든다.

| 명령·도구 | 목적과 입력 | 처음 읽을 항목·종료 |
| --- | --- | --- |
| `ps -eo pid,ppid,comm,args` | Linux에서 프로세스 목록을 한 번 출력한다. `-e`는 전체, `-o`는 표시할 항목을 지정한다. | PID·PPID·실행 인자. PPID는 부모 프로세스 번호이며 Gradle JVM과 앱 JVM을 구분한다. 출력 후 종료. |
| `top -p <PID>` | 확인한 앱 PID만 반복 관찰한다. `<PID>`는 실제 번호로 바꾸며 꺾쇠는 입력하지 않는다. | 처음에는 PID·%CPU·COMMAND만 본다. `%CPU`의 기준과 갱신 간격도 확인한다. `q`로 종료. |
| `top -H -p <PID>` | `-H`로 프로세스 안의 Linux 스레드를 표시한다. | CPU를 쓰는 TID와 시각을 기록한다. `q`로 종료. CPU-04에서 소개. |
| `jcmd <PID> Thread.print` / `jstack <PID>` | 대상 JVM의 스레드 덤프를 출력한다. 둘 중 접근 가능한 하나부터 배운다. | 스레드 이름·상태·스택·플랫폼 스레드의 `nid`. 출력 후 종료. 같은 사용자와 진단 도구 접근 권한 확인. |

## 세부 커리큘럼

### CPU-01 — Spring Boot도 프로세스다

- 배울 것: 프로그램과 프로세스, PID·PPID를 구분한다.
- 안내 실습: 기본 앱을 실행하고 `ps` 출력에서 실제 앱 JVM을 찾는다. Gradle JVM과 혼동되면 실행 인자를 함께 읽는다.
- 예상·가설 질문: Java 프로세스가 여러 개라면 무엇을 근거로 우리 앱을 찾을까?
- 완료 기준: 선택한 PID와 실행 인자, 선택 이유를 기록하고 재시작 후 PID를 다시 찾는다.

### CPU-02 — 정상 CPU 읽기

- 배울 것: CPU와 vCPU, 프로세스 사용률과 서버 전체 사용률, user/system CPU를 순서대로 배운다.
- 안내 실습: 아무 요청이 없는 구간과 가벼운 요청 구간을 같은 관측 길이로 비교한다. 처음에는 항목 세 개만 읽는다.
- 예상·가설 질문: 요청이 없어도 CPU 사용률이 정확히 0일까? 한 번의 숫자로 정상 범위를 정할 수 있을까?
- 완료 기준: 관측 시각·구간·표시 기준과 값을 기록하고 전체 사용률과 프로세스 값을 구분한다.

### CPU-03 — 계산량을 늘리면

- 배울 것: CPU-bound 작업과 작업량·동시성의 차이를 배운다.
- 안내 실습: 실험 프로필, 짧은 종료 시간, 동시성 상한을 먼저 설계하고 계산 API를 함께 구현한다. 동시성 1부터 시작해 한 조건씩 바꾼다.
- 예상·가설 질문: 계산 시간과 동시 요청 중 무엇을 바꿨나? CPU와 API 응답 시간은 각각 어떻게 달라질까?
- 완료 기준: 정상·부하·회복 값을 비교한다. 지연이나 특정 CPU 수치가 반드시 나와야 한다고 가정하지 않는다.

### CPU-04 — Linux 스레드에서 Java 코드까지

- 배울 것: TID, 10진수·16진수, 플랫폼 스레드의 native ID와 스택을 배운다.
- 안내 실습: Thread 입문 후 같은 부하 구간에 `top -H`와 덤프를 여러 번 수집한다. TID를 16진수로 바꿔 덤프의 `nid`와 대조하고 해당 코드 줄을 찾는다.
- 예상·가설 질문: 한 번의 덤프가 계산 위치를 대표할까? 이름이 비슷한 스레드를 같은 것으로 봐도 될까?
- 완료 기준: Linux TID → JVM 스레드 → 반복 관측한 스택 → 코드 위치의 근거를 설명한다.

## 해석할 때 지킬 경계

`top`의 프로세스 %CPU는 표시 모드에 따라 해석이 달라지며 100%를 넘을 수 있다. 서버 전체 비율과 그대로 비교하지 않는다. `ps`의 CPU 값과 `top`의 관측 구간도 같다고 가정하지 않는다. 첫 CPU 추적은 플랫폼 스레드 기준이다. 가상 스레드는 OS 스레드와 일대일로 대응하지 않으므로 별도 심화에서 다룬다.

## 수업과 기록

각 단계에서 기초 설명 → 정상 관찰 → 예상 → 조건 하나 변경 → 실제 관찰 → 가설과 검증 → 정리 순서로 진행한다. 도구 입문은 장애 주입이나 해결이 없어도 된다. 첫 실험은 안내형, 반복 실험은 힌트형, 마지막 적용은 독립형으로 도움을 줄인다.

실제 출력과 자기 설명은 [실험 기록 양식](../../../../../../../docs/EXPERIMENT-TEMPLATE.md)으로 남긴다. 현재 이 문서는 계획이며 어떤 단계도 완료로 표시하지 않는다. 다음 단계는 고정된 날짜가 아니라 실제 관찰과 이해를 확인한 뒤 선택한다.
